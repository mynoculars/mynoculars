| **D-22** | Bounded critique loop: the critic's notes travel into the next compile pass (grounded rewrite, never a blind retry), bounded by `max_revisions`. | `agents/compilation.py::compiler_node`, `critic_node` |

| **D-24** | Cross-run semantic memory: retrieval reranked by similarity × volatility-aware decay (never a hard TTL); only evidence from a **passed** critique is written back. | `memory/semantic_memory.py` |
| **D-25** | Typed specialist workers: a `SearchTask.tool_hint` field (default `""`) lets a task-producing node route a task to a NAMED specialist worker instead of the default corpus search — today the only specialist is `"mcp"` (P2-13's tool), gated behind `settings.mcp_enabled`. `task_utils.py::cap_and_filter` is the only place a raw hint is ever validated against what's actually wired into the run; `orchestration/graph.py::dispatch_tasks` trusts it and just routes. Implemented, P2-14. | `state.py`, `agents/task_utils.py`, `orchestration/graph.py`, `cli.py` |
| **D-26** | Retrieval tools are mediated through a plain callable seam today (`ToolFn`) — the original design's MCP stand-in (D-30) is now the SAME seam, not a replacement of it: `tools/corpus_search.py` and `tools/mcp_client.py` are both `ToolFn` implementations, chosen (and, since P2-14, combined) at `cli.py`'s wiring layer. Implemented, P2-13. **Concurrency, fixed**: `scripts/mcp_corpus_server.py`'s tool handler is `async def` and offloads the blocking corpus lookup to a dedicated `ThreadPoolExecutor` (`mcp_max_workers`), instead of the original synchronous handler that blocked FastMCP's single event loop per call. A second, separate stall (the first-ever `qdrant_client` import happening lazily on a worker thread while the event loop was already doing real overlapped I/O, ~120s independent of any configured timeout) was found and fixed by importing `qdrant_client`/`opensearchpy` eagerly at module load. Confirmed live: 6 concurrent calls, 13.5s wall time vs 79.2s summed (ratio 1.02). See `README.md` Limitations #6 / `OPERATIONS.md` Troubleshooting for the full account. Off by default (`MCP_ENABLED=false`), never a correctness bug either way. | `tools/corpus_search.py`, `tools/mcp_client.py`, `scripts/mcp_corpus_server.py` |

Implemented, P2-10. | `storage/qdrant_store.py`, `memory/semantic_memory.py` |
| **D-28** | Interrupt idempotency: an interrupting node **re-executes from its top** on resume — it does not resume mid-function. No non-idempotent effect may precede `interrupt()`; `escalation_history` is appended only in the resume-path update for exactly this reason. Resume taxonomy: approve / redirect / abort. | `agents/escalation.py` |
| **D-29** | `model_config = ConfigDict(extra="forbid")` on every state model — schema-level pollution defense at construction time, complementing D-15's runtime worker-return whitelist. Two layers, two distinct failure modes. | `state.py` |

Implemented (stdio), P2-13. | `tools/mcp_client.py` |

Not yet added to `design/Research_Agent_Design.md` § 10's own decision table (this file, `DECISIONS.md`, is a SEPARATE, later consolidation -- see the preamble at the top of this file; D-32 IS formally logged here). | `llm/client.py` |
| **D-33** *(proposed)* | Live-service health checking (`scripts/check_services.py`) is a standalone, opt-in script, never a pytest test -- this repo's test suite is proudly, entirely offline (see `tests/conftest.py`'s module docstring), so a check depending on four-to-six live services has no place silently running (or silently skipping) inside that guarantee. PASS/FAIL/SKIP, not just PASS/FAIL: MCP_ENABLED=false (this repo's default) and a FastAPI server simply not running are both correct, unremarkable configurations, not failures -- conflating "not configured" with "broken" would make the tool cry wolf on every default install. The MCP check has no port or process to probe (D-30: stdio transport, no persistent server) -- it spawns a real, throwaway instance of the configured subprocess and makes one real tool call, the only meaningful liveness probe for that transport. | `scripts/check_services.py` |
| **D-34** *(proposed)* | The test suite is organized by SOURCE MODULE (`tests/unit/<module>.py`, one file per `src/research_agent/` module) plus `tests/integration/<scenario>.py` for full `graph.invoke()` runs -- not by the development phase/tier each test was originally written in. The prior five-file, phase-named layout (`test_core.py`/`test_tier2.py`/`test_tier3.py`/etc.) had `test_tier3.py` alone spanning at least six unrelated source modules by the time it reached 74 tests, defeating the "which file catches a regression in module X" question the layout should answer at a glance. | `tests/unit/`, `tests/integration/` |
| **D-35** *(Phase 3)* | Langfuse observability is isolated in one package, `research_agent/langfuse/`: `client.py` is the ONLY file that imports the `langfuse` SDK (`build_client()` returns a real client or `None`, never raises); every other business module (`cli.py`, `orchestration/graph.py`, `llm/router.py`, `llm/client.py`, `retrieval/hybrid.py`, `memory/semantic_memory.py`, `agents/gathering.py`, `agents/compilation.py`) imports only the thin public functions in `langfuse/__init__.py` (`start_trace`, `span`, `generation`, `event`, `score`, `end_trace`, `flush`, `shutdown`) and never sees an SDK object, a trace handle, or a span handle. Off by default (`LANGFUSE_ENABLED=false`): zero SDK import, zero network calls. A single generic `traced_node()` wrapper applied at `graph.py`'s 13 `add_node(...)` call sites spans every node without touching any node function body. The installed SDK is v4.x (OTel-based, no stateful `.trace()` object) — session/environment grouping goes through `propagate_attributes(...)`, verified live to survive both being read outside its lexical `with` block and LangGraph's own `contextvars`-based parallel dispatch. Nesting: `TraceContext` also accepts an optional `parent_span_id`, and the run's open root span was already tracked in `Observer._roots` for `end_trace`'s sake, so real OTel parentage needed no new state and no call-site changes; `_trace_context()` additionally yields to an already-current span of the same trace, so observations made inside a `span_ctx()` block nest under that block rather than under the root. (Earlier revisions of this row recorded flat traces as a deliberately deferred limitation — that is no longer accurate.) `Observer.span_ctx()` wraps the SDK's `start_as_current_observation` so a node span opens BEFORE the node runs and its timestamps are real; the post-hoc `span()` is kept for callers with no block to wrap, and carries `duration_ms` as metadata because a span created after the work finished would get a negative duration from a true end time. `api/server.py` opens and closes a root trace per REQUEST — not per run — because `propagate_attributes` is sync-only and attaches to the calling thread, and FastAPI serves these `def` endpoints from a reused threadpool; entering on one request and exiting on another would leak a session id onto the next request that worker handles. `create_score` takes `trace_id` ONLY: the ingestion API accepts exactly one score target and rejects `traceId`+`sessionId` together with HTTP 400, so scores inherit their session from the trace they attach to. | `langfuse/client.py`, `langfuse/observer.py`, `langfuse/helpers.py`, `langfuse/pricing.py`, `langfuse/__init__.py` |

| **D-36** | Application assembly (`AppBundle`, `build_app_and_settings`) lives in its own neutral module, `research_agent/assembly.py`, not in `cli.py`. `api/server.py` imports it from there. `cli.py` re-exports both names, so every pre-existing `from research_agent.cli import build_app_and_settings` call site keeps working unchanged. Rationale: `api/server.py` is a long-running HTTP service and was importing its entire startup path from a module named "cli" — merely odd while the API was a demonstration of the seam (D-33), actively wrong once the API is packaged and consumed by a separate project. Nothing about the assembly itself changed in the move; the function body is byte-identical. | `assembly.py`, `cli.py`, `api/server.py` |
| **D-37** | The repo is an installable artifact (`pyproject.toml`, setuptools backend, `src/` layout), not only a `PYTHONPATH=src` checkout. Optional dependency groups (`api`, `mcp`, `langfuse`, `viz`, `dev`, `all`) mirror exactly those code paths that are off by default AND lazily imported, so a core install genuinely omits FastAPI/uvicorn/MCP/Langfuse — verified in a clean venv, not assumed. A `research-agent` console script exposes the CLI. Versioning is manual SemVer in the `version` field, bumped with the change and tagged, deliberately NOT derived from git (a build-time dependency, and it hides the version from anyone reading the file). The PUBLIC surface a MAJOR bump is owed for is stated explicitly in that file's header comment: `assembly.build_app_and_settings`/`AppBundle`, the three HTTP request/response shapes, the console script's arguments, and the `.env` setting NAMES — everything else is internal. `requirements.txt` is unchanged and remains the development pin-set; `pyproject.toml` is what a consumer resolves against. | `pyproject.toml` |

| **D-38** | **Retrieval is a LADDER, not a single tier.** `tools/retrieval_chain.py` tries corpus -> ONE reformulated corpus retry -> MCP -> the answering model's own knowledge (`tools/model_knowledge.py`), stopping at the first tier returning evidence above `min_evidence_score` (the same predicate D-17 uses for coverage, passed in so the two can never drift). Rationale: before this the system had exactly one tier, and a corpus that did not contain the subject produced "the retrieved evidence does not cover it" -- reporting a RETRIEVAL limitation as an absence of knowledge, which is the wrong answer to give. Honesty invariants, all enforced: model-sourced items always carry `source="model"` and are never relabelled; `compile_report`'s old GROUNDING RULE (which forbade model knowledge outright, and was therefore the direct cause of the failure) is replaced by an ATTRIBUTION RULE requiring model-derived claims to be marked as general knowledge in the prose; `critique` is told not to fail a report for using attributed model knowledge; telemetry reports `corpus_recall` and `model_sourced_items` alongside `recall`, so "we answered it" and "the corpus answered it" can never be confused. The model tier is LAST, so a real document always wins. Off by one flag (`MODEL_KNOWLEDGE_ENABLED=false`) restores the exact pre-D-38 posture, escalation included. | `tools/retrieval_chain.py`, `tools/model_knowledge.py`, `prompts/templates.py`, `assembly.py`, `config.py` |
| **D-39** | **A tier "answered" only if its evidence is on TOPIC, not merely high-scoring.** `retrieval_chain._sufficient` now requires one shared distinctive term (4+ chars, minus query scaffolding) between the query and a hit that cleared `min_evidence_score`. Rationale: RRF score is an ORDINAL signal -- "best of what came back" -- and a fixed-k search over a small corpus always returns k documents, so there is no empty state and a score test alone can never fail. Live (run p205.90-check): asked for GDP per capita and demographics against a ten-document Redis corpus, both legs returned the same irrelevant documents, cross-leg agreement pushed them to ~1.0, tier 1 declared success, the model tier was never reached, and the report said the evidence did not cover it -- the exact give-up D-38 exists to remove, re-entering through the sufficiency test. One shared term is deliberately a floor against wholly off-topic matches, not a relevance ranker. | `tools/retrieval_chain.py` |
| **D-40** | **Citations are goal ids, never pasted evidence text and never internal scores.** `compile_report` specifies `[g1]` / `[g1][g3]` exactly, and forbids three things live output actually did: running the source sentence into the claim with no delimiter ("...whole blobRedis is an in-memory data store..."), printing internal bookkeeping (`[g1 \| model \| score=0.60]`) into user-facing prose, and inventing citation text for claims no evidence item supports (run p205.93-check attributed Cassandra and DynamoDB descriptions to a corpus containing neither). | `prompts/templates.py` |
| **D-41** | **The model tier gets hard anti-fabrication limits, because self-reported confidence does not catch confabulation.** `templates.model_knowledge` forbids inventing names of operations/exercises/programmes, tells the model to prefer stable facts over date-pinned ones, and requires confidence to reflect the WEAKEST part of a compound claim. Rationale: run p205.91-check emitted "the 2023 Balakot-style airstrikes" (Balakot was 2019) and several non-existent named initiatives, all above the 0.5 confidence gate -- models are most confident exactly when confabulating plausible specifics. This REDUCES the failure rate; it does not eliminate it, which is why `corpus_recall` and `model_sourced_items` are in telemetry and why the report must attribute model claims (D-38). | `prompts/templates.py` |

| **D-42** | **Model recollection never enters durable memory, and recalled memory may never re-frame a query.** `SemanticMemory.store_run` filters out `source="model"` as well as `source="memory"`; `templates.compose_goals` labels recalled facts as background from UNRELATED runs and forbids them narrowing the question. Rationale, from runs p205.96/.97-check: the army run wrote 28 memory items of which 24 were model recollection, and the next, unrelated run ("Compare India and US" — an open question that had previously produced economic and demographic goals) recalled five of them and composed an entirely MILITARY goal set, inheriting PLA-doctrine prose verbatim into an India-vs-US report. Two independent reasons the write must not happen: storing recollection caches a lookup that was never expensive, and it launders an unverified guess into something a later run reads back tagged `source="memory"`, indistinguishable from document-backed evidence, before any retrieval has run. Memory is for what RETRIEVAL found (D-24); recollection is not. | `memory/semantic_memory.py`, `prompts/templates.py` |
| **D-43** | **Citation correctness is enforced deterministically where it can be, and asked of the critic where it cannot.** `compilation._clean_citations` strips any verbatim run of an evidence item's own content from the prose (run p205.95-check pasted source sentences into claims) and drops `[gN]` markers naming goals that retrieved nothing, counting both into telemetry as `citations_pasted_evidence_removed` / `citations_to_unevidenced_goals`. What code cannot do is judge whether an EVIDENCED goal's evidence supports a given sentence — run p205.98-check cited `[g5]` for Netflix/Cassandra petabyte figures while g5's evidence was Redis session-caching text, with `model_sourced_items: 0` — so `templates.critique` now explicitly requires failing a report whose named entities, figures or dates appear in no evidence item of any source, and checking markers rather than trusting them. Deterministic half and semantic half, stated separately because they have different reliability. Also in this decision: `corpus_recall` applies the D-39 topical gate (it reported 1.0 against a Redis corpus for army and India-vs-US queries, fooled exactly as the ladder's old sufficiency test was); `complete_json` retries every sentinel segment rather than accepting complete()'s prose-correct first-segment choice (raw_chars 2895 → kept_chars 21 was costing a fallback hop on every structured call); and `generate_gaps` must spread tasks across uncovered goals (one cycle tagged all six tasks g1, the next all six g5). | `agents/compilation.py`, `prompts/templates.py`, `llm/client.py` |
| **D-44** | **The topical gate scales with query specificity, and an E4 redirect reaches retrieval.** (a) `retrieval_chain._sufficient` now requires `min(3, max(1, len(terms)//4))` shared distinctive terms, not one. Live (run p205.101-check): a nine-term query naming Redis, Cassandra, DynamoDB and petabyte scale matched a Redis session-caching document on the single word "redis", which stopped the ladder at tier 1, left `model_sourced_items` at 0, and produced a report saying "no retrieved evidence quantifies..." for all five goals — the give-up re-entering through a too-permissive gate. A long, specific query matching only on its one broad subject word is not a topical match. (b) E4 redirect routes to `gap_generator` with `human_guidance` set, not straight back to the compiler. Live (run p205.103-check): guidance asking for "inputs from global watchdogs, UN reports of press freedom, human rights abuses, democracy index" is a request for NEW EVIDENCE; recompiling the same evidence block cannot serve it, so revision 3 failed on identical missing support and re-raised E4. `critique_notes` still carries the guidance so the next compile sees it. Bounded by `max_escalations` as before. | `tools/retrieval_chain.py`, `agents/escalation.py` |
| **D-45** | **Deterministic citation repair only strips GLUED pastes, and prompts carry no worked examples.** (a) `_clean_citations` removed every verbatim occurrence of an evidence item's content; on an in-corpus query the compiler legitimately states corpus sentences almost word for word, so run p205.107-check -- retrieval perfect at `corpus_recall` 1.0 with 36 corpus items -- shipped six EMPTY report sections ("### Scalability", "### Security", "### Common Use Cases"...). The defect D-43 targeted was never quoting, it was the missing delimiter: the source sentence running into the claim with no boundary. That signature is exactly detectable as a preceding alphanumeric character, so only those are stripped now. (b) Five prompts carried concrete worked examples of past failures. The critique prompt's example -- a report citing `[g5]` for Netflix/Cassandra petabyte figures -- was echoed by the critic as a finding during a Redis vs Memcached run, and the compiler then wrote a section denying it. Rationale for a rule belongs in the code comment beside it, never in the prompt text: anything in a prompt can surface in the output. All five are now abstract, with the live evidence kept in comments. | `agents/compilation.py`, `prompts/templates.py` |

| **D-46** | **The critic is shown the evidence it is asked to verify against.** `templates.critique` took only the query, report and goals — yet D-43 instructs it to fail any named entity, figure or date that appears in no evidence item. That check was unanswerable: the critic had to guess. Live (runs p205.111/.112-check): both off-corpus reports were failed with "not supported by any evidence item" for figures the model tier HAD supplied (`model_sourced_items` 24 and 20) but which the critic never saw, costing two revisions and an E4 escalation on every off-corpus run. `critique()` now receives `state.evidence` and renders it source-tagged inside an `<evidence>` block, with an explicit reminder that items tagged `model` are evidence too. Bounded by the same 60-item tail the compiler uses. | `prompts/templates.py`, `agents/compilation.py` |
